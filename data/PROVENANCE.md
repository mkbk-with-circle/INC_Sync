# Evidence provenance

This package was drafted from `paper/inc_moe_sync_outline.md` in the parent research
project and revised on 2026-09-14 when the manuscript moved from the earlier H100 Hybrid
measurements to the H200 cross-node Direct campaign. No experiment was run to produce
this manuscript. Every number in `sections/05-evidence.tex` traces to a file under
`data/h200/numbers/` in the parent project.

## Measured numbers

- `baseline-gates.csv` carries the values the manuscript actually prints. The sixteen
  `micro` rows reproduce `data/h200/numbers/PAIRED_CONTROL_SHARE.md` and appear in
  Table 2 (`tab:paired`). The four `e2e` rows reproduce the `e2e` array of
  `data/h200/numbers/outline_shares.json` (field `pre_share_percent`) and appear in
  Table 4 (`tab:e2e`).
- T=8 and T=128 were acquired in one session; T=32 and T=64 were added later on the same
  post-stage ABI instrumented image. All four use the same three-run, 200-iteration
  protocol, but they are not one continuous sweep. The T=64 Dispatch signal window has a
  between-run deviation of 0.84 us, so the manuscript does not claim a strict ordering of
  absolute signal durations in T.
- Table 3 (`tab:fits`) reproduces the `pre` and `post` rows of
  `data/h200/numbers/CROSS_MIN_FITS.md`. Coefficients are fitted per EP size on
  T in {8, 32, 128}; T=96 is an independent hold-out and the model was not refitted
  after seeing it. Maximum hold-out error is 0.96% for entry and 4.39% for the tail
  envelope. The later T=64 points are not part of this fit or its hold-out and must not
  be folded into it retroactively.
- Figure 3 (`figures/h200_direct_sync_min_fit.pdf`) is generated by
  `paper/figs_outline/plot_h200_direct_sync_fit.R` directly from `cross_min_node.json`
  and `cross_min_fits.json`. It uses `cairo_pdf` so that font subsets are embedded,
  which the base `pdf()` device does not do.
- Microbenchmark configuration: two H200 nodes, 4 ranks each (EP8), H=7168, topk=8,
  E=256, BF16, balanced uniform routing, GIN/GDAKI on traffic class 162, DeepEP V2 at
  commit `01dc3aaa` with Direct selected and Hybrid disabled. Each grid point is three
  independent process runs of 200 active iterations.
- Serving configuration: Qwen3-30B-A3B, BF16, H=2048, 128 experts, vLLM 0.27 with
  DeepEP V2 Direct and real model routing, decode with 128 input and 128 output tokens,
  EP8 held fixed while only topology varies.

## Measurement conventions the prose must respect

These are not stylistic choices; violating them would misreport the data.

- Total operator latency is measured trace-off, phase durations trace-on. The two are
  never mixed, and a phase duration is never subtracted from a trace-off total.
- Reported uncertainty is the standard deviation *across the three runs*, not across
  iterations.
- Rank selection is per-iteration minimum: for each iteration the rank with the
  *shortest* phase duration is selected, and its duration is divided by that same
  rank's traced operator span in that iteration. The entry and signal columns select
  independently, so they may name different ranks and are never summed.
- The wide tail envelope is not a synchronization measurement. Its start can precede the
  first remote payload injection, so it covers data work, TMA waits, and GIN flush. See
  `TAIL_PATH_AUDIT.md` and `data/h200/numbers/POST_WINDOW_DIAGNOSIS.md`. The manuscript
  draws tail conclusions only from the narrow signal window.
- The narrow signal window still contains GPU-side initiation, polling, and any wait on
  a not-yet-ready peer, so it bounds control traversal from above and is not a bare
  network RTT.
- E2E shares are of GPU step time, not of request wallclock, and are not a bound on any
  end-to-end speedup. The three repetitions are client windows against one server
  instance, not three independent restarts.
- The microbenchmark and serving configurations differ in H and expert count, so their
  absolute durations cannot be composed.
- No measured share is converted into a speedup anywhere in the manuscript.

## Retired data

The H100 two-node Hybrid entry-barrier rows (11.10 us / 22.5% at EP8, T=8, from
`data/h100/KEY_NUMBERS.md`) were removed from the manuscript on 2026-09-13. Hybrid
Dispatch's final barrier is scale-up only, so it is a secondary entry-overlap scenario,
and the H200 campaign measures both boundaries on the primary cross-node Direct path
from the same instrumented runs. The H100 LL/V2 comparison was removed earlier, on
2026-09-07; its configuration metadata was never cross-checked. Neither is cited in the
current manuscript. Both records are retained in the parent project for the authors.

## Local source inspection

Synchronization stage *existence* is established from source, not measured:

- DeepEP `01dc3aaac82068020353dce2c302e38153c0bfaa`, under
  `moe_sync_experiments/third_party/DeepEP.official/`.
- NCCL `7b83616df3ae082a1f32bb74c27458bfe8153a13`, under
  `moe_sync_experiments/third_party/nccl.official/`.

These directories include local instrumentation changes, so the base commit ids are not
hashes of the complete measured source tree. Relevant files:

- `deep_ep/include/deep_ep/impls/dispatch.cuh`, `combine.cuh`: Direct entry and tail
  barriers, the primary scenario.
- `deep_ep/include/deep_ep/impls/hybrid_dispatch.cuh`: tail is explicitly scale-up only;
  scale-out data has already been consumed by forwarders.
- `deep_ep/include/deep_ep/impls/hybrid_combine.cuh`: per-channel flush, remote-tail
  update and wait; no additional epilogue barrier.
- `csrc/elastic/buffer.hpp`: staging layout and final tensor allocation.
- `contrib/nccl_ep/device/hybrid_ep.cuh`: cross-round RDMA guard and local completion.

The wording is deliberately snapshot-specific. General GIN ordering is cited to NVIDIA's
online documentation, accessed September 2026. `TAIL_PATH_AUDIT.md` records the revised
tail audit with immutable source URLs and line anchors: cross-node Direct has a distinct
sender-completion and local-join stage before the EP-wide signal exchange, and GDAKI
flush waits for send-CQ progress while the public API does not equate that return with
remote GPU visibility.

- Figure 1: native TikZ reconstruction of the readiness/completion concept. Schematic
  coordinates, no measured timing scale, no external artwork.
- Figure 2: PGFPlots evaluation of `gain/L = k - epsilon/L` for k=1 and k=2. Analytical

  RTT.

## Draft status

No in-network hardware measurement, post-visibility decomposition, wire protocol, or
serving evaluation of the design is claimed. The three quantities that would pin down
the achievable tail saving are sender completion, destination visibility, and
signal-based release observed separately on one cross-node Direct configuration; none
has been measured. Authors and affiliations are deliberately unfilled. This directory is
a compilable draft, not a submission record.
