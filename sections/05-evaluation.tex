\section{Evaluation}
\label{sec:evidence}
We ask three questions: how pre-barrier cost changes with token count, how it appears across EP configurations, and how much of an MoE serving step it occupies.

\subsection{Experimental Setup and Methodology}
\label{sec:setup}
Each node has eight H200 GPUs connected by NVSwitch and eight 400\,GbE RoCE interfaces. Cross-node runs use GIN's GDAKI backend, traffic class 162, PyTorch 2.13, CUDA 13, NCCL 2.31.2, and DeepEP V2 based on commit \texttt{01dc3aaa}~\cite{deepepcode}. Direct is selected with Hybrid disabled; available local communication within Direct is retained.

Microbenchmarks use $H=7168$, $\topk=8$, 256 experts, BF16, and balanced uniform routing. $T$ denotes tokens per rank. Each configuration has three process runs with 200 measured iterations. For each iteration, we report the shortest pre-barrier across ranks and normalize it by the same rank's trace-on operator time. Results are averaged over iterations and runs; error bars show variation across run means.

The EP8 token sweep and the EP-size comparison are separate campaigns. \autoref{fig:entry-cost} uses $T=8,32,64,128$ from one instrumented image. \autoref{tab:entry-constants} uses its listed points from the original campaign plus a later EP8/T64 batch; its constants are fitted only to those values.

\subsection{Pre-Barrier Cost versus Token Count}
\label{sec:entry-eval}
\autoref{fig:entry-cost} reports pre-barrier duration and its share within a single Direct Dispatch or Combine operator at EP8. Dispatch and Combine remain near 15\us{} across the measured token counts. Their operator shares fall from 20.57\% and 19.84\% at $T=8$ to 4.88\% and 5.05\% at $T=128$. Small batches therefore expose a larger fraction of each communication operator to readiness coordination.

\subsection{Pre-Barriers in MoE Serving}
\label{sec:e2e}
We measure Qwen3-30B-A3B in BF16 with vLLM 0.27 and DeepEP V2 Direct. The model has $H=2048$, 128 experts, and $\topk=8$. Runs use actual routing, TP=1, EP8, and requests with 128 input and 128 output tokens. \autoref{fig:inference-share} reports one-node measurements at concurrency 1, 64, 128, and 256, and cross-node measurements at 64 and 128.

The serving build includes tracing and an expert-padding correctness fix. For decode, one active GPU step is sampled per rank and client window; each sampled step contains 48 Dispatch and 48 Combine calls. We sum the pre-barrier intervals from those calls, divide by the same rank's trace-on GPU-step time, and average over ranks and three client windows on the same server instance. Thus \autoref{fig:inference-share} and \autoref{tab:serving-coverage} measure cumulative pre-barrier exposure within an MoE GPU step, whereas \autoref{fig:entry-cost} measures a single communication operator.

\input{figures/inference-share}

For one node, the shares at C64, C128, and C256 are 9.33\%, 7.94\%, and 7.61\%. C1 is a low-load anchor with only one active rank in each sampled window. Across two nodes, C64 and C128 give 16.72\% and 15.19\%. Readiness coordination therefore remains visible with real routing and model computation.

\autoref{tab:serving-coverage} extends the cross-node results. At 16 tokens per rank, the share remains near 15\% across EP4, EP8, and EP16. Prefill has much larger token batches and a 2.6--3.1\% share. Each prefill row samples the single active prefill step per client window; it is a workload comparison rather than a controlled token-only experiment.
