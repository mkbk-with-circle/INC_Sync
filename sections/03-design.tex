\section{Design}
\label{sec:design}
\sys{} coordinates readiness during data upload and generates destination completion notifications on the managed network path. This section describes those operations and the resource contracts they require.

\subsection{Overview and Assumptions}
\label{sec:overview}
Figure~\ref{fig:design-overview} contrasts the baseline with our two changes: uploading during readiness aggregation and appending completion notifications to trailing data.
\input{figures/design-overview}
The \sys{} node receives readiness signals and data from all participating ranks. For each communication round, it keeps track of (i) which ranks are ready, (ii) how many records each rank will send to each destination, (iii) how many records have been forwarded to each destination, and (iv) which round owns each destination buffer. It also buffers early-arriving data within a fixed capacity. A generation identifier distinguishes communication rounds and their buffer uses. We assume reliable, ordered delivery: observing \done{} means that all data it covers is visible in the destination GPU's memory.

Receive buffers are allocated and registered symmetrically during initialization. Their layout, address mappings, capacities, and access information are established with INC once. Each token carries routing and record information that determines its destination and staging offset without global receive counts. For each generation, \ready{} confirms that the designated receive region is free from prior use and writable; it does not republish the memory descriptors. Sources upload directly, subject to PFC backpressure on network staging. Compact expert placement can be computed separately.

The design can apply within or across nodes, provided all traffic covered by \done{} passes through INC and ordered delivery extends to the destination GPU. Hierarchical or multi-rail paths require completion tracking across all forwarding stages; observing an intermediate hop is insufficient. We study cross-node Direct as the baseline scenario, without assuming that its results establish benefits for other topologies.

\subsection{Readiness Aggregation and Early Upload}
\label{sec:early-upload}
After routing and local preparation, rank $s$ sends \ready{} together with its buffer epoch and a count vector: element $d$ gives its planned number of output records for destination $d$. It then uploads \data{} without a staging-credit request or a wait for other ranks. INC marks the rank ready only after accepting the complete message for the current generation; duplicate or stale announcements do not update the state. The node buffers early data and begins accumulating vectors as they arrive.

Once all required \ready{} messages have arrived and destination staging is writable, INC parses token routes and fans out buffered and arriving data, subject to output capacity. Vector accumulation proceeds in parallel and need not finish before fan-out starts. Thus, readiness receipt gates forwarding, while finalized counts gate completion notification. Local routing and count-vector construction remain source-side work.

The readiness dependency remains: the network cannot deliver into an unready destination. What changes is that the source-to-node transfer can proceed while readiness is being aggregated. The node's location permits this transfer to share the eventual data path. Whether the head start reduces operation latency depends on the slowest required source and the output queue, as analyzed in Section~\ref{sec:readiness-analysis}.

For Dispatch, global receive counts and final expert offsets can be computed alongside transfers into reserved staging. Count-vector entries must match the records actually emitted by fan-out, including any replication. Hardware can pipeline the integer additions with upload and forwarding; any remaining aggregation delay is included in completion latency. Multicast bandwidth savings are separate from the synchronization mechanism.

\subsection{Completion Notification}
\label{sec:completion-design}
For Dispatch generation $g$, source $s$ sends a count vector with \ready{}, where $n_{g,s,d}$ is the number of output records planned for destination $d$. INC sums these vectors while forwarding data:
\begin{equation}
 N_{g,d}=\sum_s n_{g,s,d}.
 \label{eq:count}
\end{equation}
The total is final once all required vectors, including zero counts, have been received and aggregated. INC tracks forwarded records in the same units, counting each record once and only after all its fragments enter the ordered output channel.

INC appends \done$(g,d)$ when (i) $N_{g,d}$ is final, (ii) destination $d$ is ready, and (iii) all $N_{g,d}$ records have entered that channel. The delivery path must preserve data-before-notification ordering through to destination memory:
\begin{equation}
 \operatorname{observe}_d(\done(g,d))
 \Rightarrow
 \bigwedge_{x\in\mathcal{D}_{g,d}}\operatorname{visible}_d(x),
 \label{eq:visible}
\end{equation}
where $\mathcal{D}_{g,d}$ is the expected input at $d$. Thus, \done{} establishes input availability for that destination; any additional application dependencies still apply.

For Combine, INC retains the expected contributor set established during Dispatch. Contributors are identified by route slot, distinguishing experts even on the same rank. INC reduces their weighted partials~\cite{dysharp,switchml} and appends \done{} only after all expected contributions for the covered tokens have arrived and their reduced outputs have entered the ordered output channel.

\subsection{Buffer Management and Progress}
\label{sec:resources}
A destination sends \ready{} only after prior users of the designated receive region have finished. This commits the region to the announced generation and epoch. After observing \done{} and satisfying local requirements, Dispatch can compact the received records for expert computation; Combine can release the reduced result to its consumer. The last consumer releases the region locally; a subsequent \ready{} authorizes reuse for the next generation. Emitting \done{} alone never permits overwrite.

The sender also retains its source buffer until the transport has finished reading it. Generating target notification in the network decouples the target's release from the sender's completion path; it does not remove source-lifetime tracking. Different generations therefore require separate ownership state.

Network capacity covers early arrivals, input/output imbalance after release, and any reduction accumulators. Staging occupancy drives PFC backpressure~\cite{pfc}, pausing upstream DATA before capacity is exhausted. Headroom covers data already in flight until the pause takes effect. Upload resumes on the same path when space becomes available; no per-generation credit exchange is required.

\ready{} and count-vector messages use a separately provisioned control class that retains progress when DATA is paused. Otherwise, a full staging queue could block the readiness messages required to drain it. Resource limits must feed backpressure before overflow, including limits on reduction state. Pauses can reduce overlap or throughput. Recovery from endpoint or network-node failure is outside the assumed reliable-delivery model.
