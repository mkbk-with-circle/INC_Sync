\section{Design}
\label{sec:design}
\sys{} collects readiness signals while ranks upload data and notifies each destination when its input is complete.

\subsection{Overview and Assumptions}
\label{sec:overview}
Figure~\ref{fig:design-overview} shows the two changes: uploading while collecting \ready{} and sending \done{} after the last data for each destination.
\input{figures/design-overview}
INC tracks (i) which ranks are ready, (ii) how many tokens or reduced results each destination should receive, (iii) how many have been forwarded, and (iv) which communication round uses each receive buffer. It also buffers early-arriving data. A generation identifies a Dispatch or Combine round; a buffer epoch distinguishes successive uses of the same buffer. We assume reliable, ordered delivery: a destination observes \done{} only after the associated data is visible in its GPU memory.

Receive buffers are allocated and registered symmetrically during initialization. INC obtains their layout, address mappings, sizes, and access permissions once. Each token carries routing information and an identifier used to compute its destination buffer offset without global receive counts. \ready{} confirms that the previous round has finished using the receive buffer and that it is writable for the current round. Sources upload directly; PFC pauses DATA transferring when network buffers approach capacity.

The design applies within or across nodes if all relevant traffic passes through INC and data-before-DONE ordering holds through to the destination GPU. With multiple forwarding stages or network rails, completion tracking must include every stage.

\subsection{Readiness Aggregation and Early Upload}
\label{sec:early-upload}
After computing its routes and local token counts, rank $s$ sends \ready{} with its buffer epoch and a count vector. Element $d$ specifies how many token copies it will send to destination $d$. The rank then uploads \data{} without waiting for other ranks. INC accepts one complete READY/count-vector message per rank and round, ignores duplicates and old messages, and sums the vectors as they arrive.

Once all required \ready{} messages arrive and destination buffers are writable, INC reads each token's route and forwards it to the specified destinations. Forwarding can start before the vector sum finishes; INC needs the final count only when deciding to send \done{}. Both the announced counts and the forwarding counters count the token copies sent to each destination.

This allows upload to overlap waiting for other ranks. The latency reduction depends on rank readiness times and network queuing (Section~\ref{sec:readiness-analysis}). Global receive counts and final expert-buffer offsets can be computed while tokens enter the preallocated receive buffers. Hardware can pipeline the vector additions with transfer, although any unfinished additions delay \done{}.

\subsection{Completion Notification}
\label{sec:completion-design}
For Dispatch round $g$, let $n_{g,s,d}$ be the token count sent by source $s$ for destination $d$. INC sums the count vectors to obtain the expected receive count:
\begin{equation}
 N_{g,d}=\sum_s n_{g,s,d}.
 \label{eq:count}
\end{equation}
Every source supplies a vector, including destinations for which it sends no tokens. INC also counts forwarded tokens, incrementing the counter once per token copy after its complete payload has been submitted for delivery.

INC sends \done$(g,d)$ when (i) it has summed the count vectors from all required sources, (ii) destination $d$ is ready, and (iii) it has submitted all $N_{g,d}$ token payloads for delivery. DONE must become visible only after those payloads are visible in destination memory:
\begin{equation}
 \operatorname{observe}_d(\done(g,d))
 \Rightarrow
 \bigwedge_{x\in\mathcal{D}_{g,d}}\operatorname{visible}_d(x),
 \label{eq:visible}
\end{equation}
where $\mathcal{D}_{g,d}$ denotes the expected input at $d$. DONE confirms that this input is available; the destination must still satisfy any other dependencies before computation.

For Combine, INC uses the expert assignments recorded during Dispatch to determine which outputs are expected for each token. Each expert output carries its top-$k$ slot index, distinguishing experts on the same rank. INC sums the weighted expert outputs~\cite{dysharp,switchml} and sends DONE after all expected outputs have arrived and all reduced results for the destination have been submitted for delivery, with the same ordering guarantee.

\subsection{Buffer Management and Progress}
\label{sec:resources}
\ready{} confirms that the receive buffer is available for the current round. The buffer remains reserved until its last reader finishes; DONE confirms data arrival, not permission to overwrite. Source buffers are retained until the sender finishes reading them. Generation and buffer-epoch checks reject stale signals. Generation and buffer-epoch checks reject stale signals.

INC uses PFC~\cite{pfc} to pause DATA before token buffers or Combine partial-sum storage fill up, reserving headroom for data already in flight. Transmission resumes when space becomes available. READY and count vectors use a separate traffic class with reserved resources, preventing DATA pauses from blocking the signals needed to start forwarding. Backpressure protects finite storage but can reduce overlap or throughput.
