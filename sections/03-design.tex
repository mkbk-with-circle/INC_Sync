\section{Design}
\label{sec:design}
\sys{} moves readiness aggregation to INC so that ranks can upload data while waiting for their peers.

\subsection{Overview and Assumptions}
\label{sec:overview}
Figure~\ref{fig:design-overview} contrasts the baseline's wait-before-send sequence with early upload.
\input{figures/design-overview}
INC maintains a bitmap of ready ranks and a bounded queue of early data for each communication round. A generation identifies the Dispatch or Combine operation, and a buffer epoch identifies a particular use of a receive buffer. All participating ranks and the traffic controlled by their pre-barrier must be covered by the INC node.

Receive buffers are allocated and registered symmetrically during initialization. INC obtains their layout, address mappings, sizes, and access permissions once. Token routes and identifiers determine destinations and buffer offsets without global receive counts. This allows data to enter preallocated receive buffers while the final expert layout is being computed.

A rank sends \ready{} after its local input is available and the previous use of its receive buffer has finished. READY identifies the rank, generation, and buffer epoch. The node uses it to confirm that the buffer is writable for the current round. Deployment can be within or across nodes; any path that bypasses INC needs the corresponding readiness protection before it writes destination memory.

\subsection{Early Upload and Readiness Aggregation}
\label{sec:early-upload}
Each rank sends READY, then uploads locally available tokens with their routing information. Dispatch counts and other metadata follow the library's normal processing schedule. READY does not wait for a complete count vector.

INC accepts one readiness announcement per rank and round, ignoring duplicate and stale announcements. Before all required ranks are ready, arriving data stays in network staging. After readiness is complete, INC forwards buffered and newly arriving tokens to their destinations at the available output rate. The forwarding condition is the same for every packet in the round: the required ranks have announced readiness and the destination buffer matches the announced epoch.

For Dispatch, the destination arranges received tokens into expert inputs using the routing and count metadata. For Combine, the same upload-and-forward sequence carries expert outputs back to their token owners for combination. Delivery acknowledgments and local processing determine when received data can be consumed and source buffers can be reused.

The source-to-INC transfer overlaps readiness collection. This can advance destination delivery when the output link can drain early data without introducing an equal or larger delay.

\subsection{Buffer Management and Backpressure}
\label{sec:resources}
A receive buffer remains assigned to its round until the last computation reading it finishes. The next READY confirms that it can be reused. A source buffer remains allocated until sending hardware has finished reading it. Generation and epoch checks keep old messages from authorizing writes into a newer round. INC retires a round's readiness state after its queued data has drained and all participants have advanced to the next round.

Network-buffer occupancy triggers PFC~\cite{pfc} before overflow, with headroom for data already in flight when a pause is sent. Upload resumes on the same path when capacity becomes available. READY uses a separate traffic class with reserved resources so that DATA pauses cannot block the signals needed to start forwarding. Required control metadata receives the same progress guarantee.
