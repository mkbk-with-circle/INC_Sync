\section{Introduction}
\label{sec:intro}
Mixture-of-experts (MoE) inference uses Dispatch to send token activations to selected experts and Combine to return their outputs. Expert-parallel (EP) communication libraries optimize this movement through GPU-initiated transport, staging buffers, and topology-aware transfers~\cite{deepep,ncclep}. Small batches also make control latency significant: a sender may wait for peer readiness before sending an available token, and a receiver may wait for a completion notification before using delivered data.

We focus on cross-node DeepEP V2 Direct Dispatch and Combine. In this implementation, a pre-barrier precedes payload injection. At the other boundary, sender completion and local coordination precede the post-barrier signal exchange across the EP group~\cite{deepepcode}. This placement serializes parts of coordination with data movement. It is a property of the chosen path; other EP implementations have different readiness and completion protocols.

Measurements on two H200 nodes show why these boundaries matter. At EP8 and eight tokens per rank, the pre-barrier occupies about 20\% of the traced operator. Increasing the token count to 128 reduces its share to about 5\%, while the absolute pre-barrier duration remains close to 15\us{}. In Qwen3-30B-A3B decode at fixed EP8, the pre-barrier accounts for 15.2--16.7\% of the sampled cross-node GPU step, compared with 7.9--9.3\% on one node. These measurements motivate the question: can pre-barrier and post-barrier communication overlap data transfer while preserving the conditions required by the consumer?

We propose \sys{}, which places coordination at a network node on the data path. Each rank announces readiness and uploads directly into network staging. The node aggregates readiness while data is in flight, buffers early data, and forwards it when the destination buffers are writable. It also tracks the expected receive count for each destination and sends ordered DONE after its last data.

This organization preserves two separate obligations. The receiver must obtain complete, visible input before computation begins, and buffers cannot be reused until the last computation using them finishes. Moving target notification into the network does not remove the need to retain source buffers during transmission or genuine global dependencies. Existing multicast and reduction can be used in the data plane; their bandwidth benefits are separate from the timing changes studied here.

The analysis follows readiness, data visibility, and the start of dependent computation as distinct events. We borrow Swift's separation of endpoint and fabric delay~\cite{swift} to avoid treating a measured GPU barrier as a network RTT. Unequal readiness times, finite staging, and output service determine whether early upload advances completion. At the tail, the benefit depends on the exposed interval between destination data visibility and baseline notification. In a symmetric reference where each boundary adds one exposed one-way traversal, the two opportunities sum to one fabric RTT before the design's added cost.

This paper makes three contributions. First, it measures the pre-barrier and the post-barrier signal window of cross-node Direct, including pre-barrier costs in a real MoE serving stack. Second, it specifies network readiness aggregation and ordered completion notification with explicit resource and visibility requirements. Third, it provides a latency model for identifying when these mechanisms shorten the critical path. The evaluation characterizes existing software baselines; it does not include an INC prototype or measured INC speedup.
