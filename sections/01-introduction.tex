\section{Introduction}
\label{sec:intro}
Mixture-of-experts (MoE) inference uses Dispatch to send token activations to selected experts and Combine to return their outputs. Expert-parallel (EP) communication libraries optimize this movement through GPU-initiated transport, staging buffers, and topology-aware transfers~\cite{deepep,ncclep}. Small batches also make control latency significant: a sender may wait for peer readiness before sending an available token, and a receiver may wait for a completion notification before using delivered data.

We focus on cross-node DeepEP V2 Direct Dispatch and Combine. In this implementation, an entry barrier precedes payload injection. At the other boundary, sender completion and local coordination precede an EP-wide signal exchange~\cite{deepepcode}. This placement serializes parts of coordination with data movement. It is a property of the chosen path; other EP implementations have different readiness and completion protocols.

Measurements on two H200 nodes show why these boundaries matter. At EP8 and eight tokens per rank, entry synchronization occupies about 20\% of the traced operator. Increasing the token count to 128 reduces its share to about 5\%, while the absolute entry duration remains close to 15\us{}. In Qwen3-30B-A3B decode at fixed EP8, entry synchronization accounts for 15.2--16.7\% of the sampled cross-node GPU step, compared with 7.9--9.3\% on one node. These measurements motivate the question: can readiness and completion coordination overlap data transfer while preserving the conditions required by the consumer?

We propose \sys{}, which places coordination at a network node on the managed data path. Each rank announces readiness and immediately uploads into reserved network staging. The node aggregates readiness while data is in flight, holds early arrivals, and releases them when the destination resources are usable. It also tracks a sealed traffic plan for each destination and generates an ordered completion notification after the destination's final output data unit.

This organization preserves two separate obligations. The receiver must obtain complete, visible input before computation begins, and buffers must remain protected until their last user releases them. Moving target notification into the network does not remove sender-side source-buffer lifetime requirements or genuine global dependencies. Existing multicast and reduction can be used in the data plane; their bandwidth benefits are separate from the timing changes studied here.

The analysis follows readiness, data visibility, and consumer release as distinct events. We borrow Swift's separation of endpoint and fabric delay~\cite{swift} to avoid treating a measured GPU barrier as a network RTT. Unequal readiness times, finite staging, and output service determine whether early upload advances completion. At the tail, the benefit depends on the exposed interval between destination data visibility and baseline notification. In a symmetric reference where each boundary adds one exposed one-way traversal, the two opportunities sum to one fabric RTT before the design's added cost.

This paper makes three contributions. First, it measures entry synchronization and the completion-signal window of cross-node Direct, including entry costs in a real MoE serving stack. Second, it specifies network readiness aggregation and ordered completion notification with explicit resource and visibility requirements. Third, it provides a latency model for identifying when these mechanisms shorten the critical path. The evaluation characterizes existing software baselines; it does not include an INC prototype or measured INC speedup.
