\section{Background and Motivation}
\label{sec:background}

\subsection{Expert-Parallel Communication}
\label{sec:epbackground}
An MoE layer selects up to $\topk$ experts for each input token. Under expert parallelism, experts are distributed across GPU ranks. Dispatch moves activations to the selected expert ranks; after expert computation, Combine returns and merges their contributions at the token owner~\cite{deepep,ncclep}.

Routing determines the amount of traffic sent to each destination. Communication therefore involves both activations or partial outputs and metadata describing destinations, valid counts, and output placement. Within a node, ranks may use NVLink; across nodes, they use a network transport such as RDMA. Communication staging provides known landing addresses, while the final expert layout may depend on exchanged counts.

Ranks exchange routing metadata, valid counts, and readiness or completion signals through collective operations or peer-to-peer writes and polling. Readiness signals indicate that resources are ready; completion signals indicate that the associated transfers have finished.

EP implementations organize these exchanges differently. NCCL EP HT gathers routing metadata before Dispatch; DeepEP V2 Direct performs a pre-barrier, then processes counts alongside data; NCCL EP LL writes into reserved slots and uses fine-grained signals without an independent pre-barrier~\cite{ncclhtcode,deepepcode,ncclllcode}. These schedules must all ensure writable receive resources, visible input before consumption, and safe buffer reuse after consumption.

\subsection{Synchronization in DeepEP V2 Direct}
\label{sec:epsynchronization}
Cross-node DeepEP V2 Direct places coordination at both ends of Dispatch and Combine~\cite{deepepcode}. A pre-barrier precedes payload injection. Dispatch exchanges counts and computes layout alongside data movement; Combine reuses the established routing. After completing the required sender-side work, ranks exchange completion signals across the EP group in a post-barrier.

The Direct path already reserves communication buffers. Any schedule change must preserve buffer lifetimes and data visibility. We focus on this cross-node path, whose pre-barrier and post-barrier exchanges expose opportunities at both transfer boundaries.

At fixed EP size, fewer tokens reduce payload work while coordination still involves the same ranks. Our EP8 measurements show a pre-barrier duration of approximately 15\us{}, occupying about 20\% of the operator at eight tokens per rank and 5\% at 128. This motivates overlap, although the measured interval is not entirely removable. Section~\ref{sec:evidence} presents the methodology and results.

\subsection{Opportunities for In-Network Computing}
\label{sec:incopportunity}
In-network computing (INC) allows switches and other network devices to compute while forwarding data, for example by summing values from multiple GPUs. These devices can also retain temporary state across packets, such as which ranks are ready and how much data has been forwarded to each destination. Prior work uses in-network computation for collective reduction and data transfer in MoE communication~\cite{sharp,switchml,dysharp}. We use this state to aggregate readiness signals and track completion, together with network buffering to overlap synchronization with data transfer.

A locally ready rank can begin uploading to network staging while INC collects readiness signals from other ranks. Destination delivery still waits for the required readiness and writable resources. At completion, INC can track expected output and append an ordered notification to the destination's final data. The notification must imply data visibility, and genuine global dependencies remain.

\paragraph{Key insight.}
Synchronization conditions must hold, but their communication need not be serialized with data transfer. INC can overlap readiness aggregation with upload and append ordered completion notifications to trailing data, potentially shortening the critical path.
